#+title: RPC
#+options: toc:2 num:t

#+begin_export rst
Two-party Cap'n Proto RPC, level 1: bootstrap, calls on imported and
promised (pipelined) capabilities, returns with capability tables,
finish/release bookkeeping, disembargo echo, abort, and the
spec-mandated ``unimplemented`` reply for level 3+ messages. The vat
is single-threaded and message-driven -- see :doc:`architecture`
section 4 for how ``rpc_pump_once`` dispatches one message at a time
and what state it updates.
#+end_export

* Call sequence

      S-->>C: Return (sum = 42)

#+begin_export rst
A *pipeline* capability (``RPC_CAP_PIPELINE``) references a
question that has not returned yet, plus a chain of pointer-field
hops into its eventual results (``rpc_pipeline_cap``). Calls on it go
out immediately; the peer resolves the hop chain against its own
in-flight answer when the dependency completes. Generated client code
(:doc:`tutorial`, part 2) always returns a pipeline-capable cap from
a bootstrap or a call that yields a capability result, so pipelining
needs no separate opt-in.
#+end_export

* Writing a server

#+begin_export rst
Extend ``rpc_server_t`` and implement ``dispatch``, or -- for
schema-generated interfaces -- extend the generated
``<interface>_server_t`` base and implement its one deferred
per-method procedure (:doc:`tutorial`, part 2.1). A capability object
stays alive as long as it has a nonzero refcount in some vat's export
table; ``rpc_ctx_export_cap`` stages a freshly minted capability
(e.g. one method's result is itself a capability) into the current
call's results. Pass ``owned=.true.`` when this vat allocated the
server: the table frees it once the refcount reaches zero, and
``rpc_conn_close`` drops every export because the peer will not
Release it. A server whose ``dispatch`` is running is freed after
that call returns, not during it. A results cap table that cannot
be written is answered with an exception Return. The flush drops the
exports it added and frees the owned servers those exports introduced,
and it frees owned servers that stayed unexported. An export from
before the flush keeps its refcount.

To opt a capability into level 2 persistence, recognize
``ctx%interface_id == RPC_PERSISTENT_IFACE`` in ``dispatch`` and
answer ``RPC_PERSISTENT_SAVE`` with an application-defined SturdyRef
in pointer field 0 of the results. The request is the generic
``Persistent<AnyPointer, AnyPointer>.SaveParams`` shape, so pointer
field 0 contains the optional ``sealFor`` owner. Clients use
``rpc_persistent_save_begin`` and ``rpc_persistent_save_wait``.
SturdyRef and Owner are realm-defined. Capnp-C++ does not define a
universal restore operation or token format, so restoration remains an
application service in both implementations.
#+end_export

* Writing a client

#+begin_src fortran
call rpc_bootstrap_send(conn, cap, err)     ! pipeline cap, usable now
call rpc_call_begin(conn, target, iface_id, method_id, m, params, qid, err)
! ... fill params content ...
call rpc_call_send(conn, m, err)
call rpc_wait(conn, qid, err)                ! pumps until qid returns
call rpc_result_content(conn, qid, content, err)
#+end_src

#+begin_export rst
Schema-generated client procedures (``<method>_begin`` /
``<method>_wait``) wrap exactly this sequence with typed parameter
and result handles; use them instead of the untyped calls above
whenever a schema is available (:doc:`tutorial`, part 2.2).
#+end_export

* Transport

#+begin_export rst
``capnp_rpc_transport`` frames each RPC message with the same
segment-table framing plain serialization uses
(:doc:`reference`, "Serialization"). ``rpc_byte_stream_t`` is its
pluggable exact-read, exact-write, readiness, and close interface.
``rpc_fd_stream_t`` adapts a descriptor and
``rpc_socketpair_streams`` creates an owned loopback pair.
``capnp_posix`` remains a thin ``bind(c)`` surface over POSIX sockets.
The three flags a non-blocking connect has to recognise come from a
small C file, because their numeric values are not the same on every
Unix. TCP, Unix-domain sockets, and socketpairs are
adapters rather than requirements of the RPC core. A TLS implementation
can provide ``rpc_byte_stream_t`` without coupling this library to a TLS
stack or certificate policy.

The three-party network layer records ``VatId{host, port}`` values from
``thirdPartyHosted`` descriptors. ``rpc_introduction_dial`` opens a
numeric IPv4 address from one of those pending introductions and
initializes a connection ready for ``rpc_accept_send``. A null dial
hook refuses every address. After the
Accept succeeds, ``rpc_introduction_done`` releases the vine.
Applications can perform DNS or directory lookup before using a custom
connection adapter.

Capnp-C++ 1.4.0 offers ``TwoPartyVatNetwork`` over an arbitrary byte
stream. Its two-party IDs deliberately cannot name a third vat, and
that release has no Provide or Accept implementation. The
``rpc-threeparty.capnp`` layer and its live TCP handoff test therefore
exercise this project's network parameterization, not C++ 1.4.0 level
3 interoperability.

For level 4 equality, ``rpc_join_send`` emits every Join part before
``rpc_join_wait`` collects the result set and settles its single
capability. Eight joins fit at once. A part that never finishes holds
its question id until Finish. The receiver groups incoming parts by
joinId and compares
local export identity only after the set is complete. Capnp-C++ 1.4.0
does not handle Join and replies ``Message.unimplemented``, so this
feature has same-language wire tests but no live C++ peer test.

``rpc_request_cancellation`` abandons an outstanding question by sending
Finish with ``requireEarlyCancellationWorkaround = false``. This is the
behavior of Cap'n Proto 1.0 and newer. A stream window counts message bodies. On a socket it is
``SO_SNDBUF``; otherwise it is 65536. ``rpc_stream_cancel`` sends the
same request for every call still in a stream window. Cancellation is
cooperative after application delivery: methods that do not opt in may
continue to completion, matching capnp-C++ ``allowCancellation``. The
live C++ interop test cancels an opted-in never-ending method and then
checks that the C++ promise was dropped.

Membranes are local wrappers.
``rpc_membrane_policy_t`` defines inbound and outbound call checks.
``inbound_redirect`` and ``outbound_redirect`` may hand back a local
server or a vat client; the call goes to that capability. A redirect
is outside the membrane: capabilities in its results stay as that
capability returned them, matching ``MembraneHook::newCall`` and
``MembraneHook::call`` (``membrane.c++`` lines 413-428 and 445-459,
``membrane.h`` lines 69-71). A call allowed through still wraps result
capabilities in the same policy. ``rpc_membrane_cap`` applies a policy
to an imported client capability, while ``rpc_membrane_server_t``
applies it to a local server capability. If a wrapper crosses back
through that policy in the opposite direction it is unwrapped,
preserving object identity by removing the wrapper.
``rpc_membrane_revoke`` marks every wrapper that shares the policy.
A later call with no redirect fails with the revoke reason.
When the policy returns a redirect, the call goes to that capability.
The server pointer from ``inbound_redirect`` or ``outbound_redirect``
is borrowed: that server must outlive the call.
A redirect chain walks at most eight hops. The policy on the last hop
is asked, and a redirect it returns is forwarded. A membrane on that
redirect is asked before the call proceeds. A repeated policy fails
the call.
On a server dispatch, name the local server. A redirect that names an
import, a local export, or a pipeline capability returns
``CAPNP_ERR_ARG`` from that dispatch. ``rpc_call_begin`` accepts those
three kinds. A client deny copies ``reject_reason`` when the policy
extends ``rpc_membrane_reason_policy_t``. A policy extending only
``rpc_membrane_policy_t`` leaves that abort reason unset. A vat client
redirect applies to ``rpc_call_begin``.
These are the applicable ``capnp/membrane.h`` semantics for the
runtime's current capability surface. No membrane state appears
on the wire.
#+end_export
